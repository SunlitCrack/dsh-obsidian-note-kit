# 本地适配层 · 运行环境能力：写入通道与限制

> 本文件记**"当前这个 agent 能用什么"**。与 `local-adaptation.md`（环境事实，同环境各 agent 下应逐字节一致）分工：那边记库与落库规则，这边记通道与能力。

## 1. 写入通道

| 运行环境 | 写 / 改笔记库的方式 | 索引刷新 | 远端命令 |
|---|---|---|---|
| **宿主 A（本机桌面端）** | ① 文件工具直写绝对路径（最稳，无依赖）<br>② 库原生工具（如知识库插件的 `kb_*` 工具族：检索 / 登记 / 收件箱 / 体检）<br>③ 库的 MCP 通道（结构化读写：按标题、块 ID、frontmatter 键精准改；移动/重命名并重写库内链接） | 手写笔记无需刷新；派生的 `<项目>/INDEX.md` 由工具维护，落后时调工具重建 | **不能**：只有本机，没有可代跑的远端目标 |

## 2. 共同限制（所有运行环境）

- **高风险动作只给步骤，不代为执行**：删库文件、批量移动/重命名、覆盖宿主配置、卸载插件、重启宿主。给出步骤与回退方案即可，是否执行由使用者决定。
- **给使用者的命令必须写明执行位置**：哪台机器、哪个环境、是否容器内。不要把执行位置留给读者猜。
- **远端证据没拿到之前不下结论**：涉及远端集群时，证据通常由使用者执行后以附件/粘贴回传；拿到之前不要在文档里替它下结论，也不要根据命令的"预期输出"先把验证结果写好。
- **命令行工具先自测再用**：各运行环境的默认 shell 与 PATH 不同。判据用 `grep`（PowerShell：`Get-Command grep`；bash：`which grep`）——**不要用 `bash` 当判据**，Windows 上它可能命中 WSL 启动器，那种 bash 不认 `/d/...` 这类路径。同名命令在不同 shell 下可能不是同一个程序（如 Windows 自带的 `find` 不支持 `-type d`）。
- **笔记直接落目标位置，不走收件箱待审中转**：知识笔记与故障文档直接写入库内目标目录；配套的手维护索引/日志当场登记完。
- **顺手改的存量内容要声明**：改 tags、补 frontmatter、修断链等超出本次范围的动作，必须在当次操作记录里写明，不许静默修改。
- **走 MCP 的写入通道在"任一侧重载"后会失效**：这类通道是 sessionful 的——客户端持 session id、服务端按 session 记状态，**服务端插件重载或宿主重启**都会把 session 清掉，而客户端仍握着旧 id，下一次调用直接报 `{"error":"Session not found"}`（换参数重试无用，也不是权限/路径问题）。处理：把该 MCP 服务器在管理器里**禁用再启用**一次重建连接（或重启宿主），并**确认连接状态**后再继续。做重载动作之后，第一次工具调用要当作可能失效来对待。
- **"写进文件"不等于"生效"**：配置类改动（frontmatter、插件 `data.json`、CSS 片段/主题片段）在宿主重新读取之前都是废纸，而各宿主的重读时点不同（进程启动 / 插件装载 / 文件监听）。固定顺序：**① 写盘 → ② 让宿主重载 → ③ 回读落盘物，确认没被回写覆盖**。反着来（先重载再改文件）会被宿主的下一次保存盖掉。
- **库原生工具的可达范围可能比你以为的窄**（实测项）：例如某些"待审区"工具只认**项目内**笔记，指向库根笔记会报 `NOT_FOUND` / `VALIDATION`；这类笔记改用文件工具直写（并在文末留来源脚注）。
- **工具报错不等于没写入**（实测项）：有的写操作报错时其实**已经落盘**（还可能重复追加），事后必须**回读目标文件**确认，必要时手工修格式。

> 最后两条与实际工具绑定，请按你环境的实测结果改写或删除；它们留在示例里是因为"**报错语义要看实现，不要用字面意义推断**"这条经验值得保留。

## 3. 通用降级顺序

① 库原生工具（如有 MCP 或插件 API）→ ② 文件工具直写绝对路径 → ③ 在可写位置生成完整文件后复制覆盖。

## 4. 能力表怎么用

- `SKILL.md` 里凡说"见适配层""按适配层要求"的地方，环境事实查 `local-adaptation.md`，能用的工具与限制查本文件。
- 换宿主时：重写本文件即可，`SKILL.md` 与 `local-adaptation.md` 都不动。
- 本文件不存在时：按 `SKILL.md` 自带的降级描述执行（通用层对适配层缺失是有兜底的）。
