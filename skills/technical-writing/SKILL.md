# 通用写作纪律（technical-writing）

把"怎么写"里**与体裁无关**的那部分抽出来，一处定义：真实性、硬性纪律、文风、内容完整性、规则怎么长。

**本文不管什么**：

| 不管 | 去哪 |
|---|---|
| 体裁骨架与字段口径——知识笔记 | `k8s-obsidian-notes` |
| 体裁骨架——故障复盘 / 报错信号卡 | `writing-postmortems` |
| 落点（哪个项目、哪个目录、文件名） | `obsidian-note-placement` |
| Obsidian 语法（wikilink / callout / frontmatter） | `obsidian-markdown` |

**与体裁 skill 的关系**：本文是写作纪律的**权威版本**。体裁 skill 里内联了同样规则，作用是兜底——防本文未被加载时规则丢失。**两者不一致时以本文为准**，并把差异回写到体裁 skill。

**适配层通常为空**：本文不含环境值（库路径、集群名、工具名），也不直接写盘，所以 `references/local-adaptation.md` 一般不需要填；`references/harness.md` 与其余 skill 共用同一份。落点与写入通道见上表各 skill。

## 0. 一句话

写之前先问三件事：**是不是真的**（真实性）→ **别人能不能照着做**（硬性规则）→ **读起来顺不顺**（文风、内容完整性）。

## 1. 真实性规则

- **不编造。** 断言必须可验证；不确定的写"待确认"并注明来源。**禁止用合理推测填充正文**——一份编得像样的文档会被当成事实引用，比承认"未记录"危害大得多。
- **信息不全先问。** 动笔前缺关键信息（时间、报错原文、影响范围、确切步骤等），**一次性列出缺失项向使用者提问**，不要带着空白开写、也不要边写边猜。使用者答不出的项写"未记录 / 未知（推算）"并注明来源。
- **来源标注与置信度。** 经验性断言三选一标注：**实测**（本环境验证过）/ **经验**（行业惯例）/ **官方**（文档数值）。指向具体证据时给出可核查的锚点（文件:行号、commit、测试名、精确查询），不写"我读过"。**来源缺失不编也不卡住**：照用事实，标 `[待补来源：谁给什么]` 占位，由使用者在定稿前补齐。
- **分清三种状态。** 写了（在仓库/文件里）≠ 上了（线上在跑）≠ 外部确认过（在外部系统核过）。说"已确认"必须写明确认了什么，不用光秃秃的对勾。
- **数字优先于形容词。** 能写数字就不写"较慢""很多"；给不出数字说明还没测出来。
- **第三方行为带日期。** 涉及他人产品（厂商、模型、API、库）的断言，版本、价格、限制一律带**观察日期**，不写成永久事实。日期只标一次、标在断言旁，不做散布全文的"新鲜度"提示。
- **远端证据没拿到之前不下结论。** 证据由使用者执行后回传，拿到之前不在文档里替它下结论，也不按命令的"预期输出"预写验证结果。

## 2. 硬性规则

- **命令可复制。** 写给"一年后照着做"的人：完整命令、真实参数、注明版本与需按实际替换的部分；不写"重新部署一下"这类转述；每步给出验证方式，危险步骤写明回退。
- **命令写明执行位置，高风险动作不代执行。** 每条命令标出**在哪台机器 / 哪个环境 / 是否容器内**执行，不把执行位置留给读者猜；删除数据、缩副本、重启生产组件、批量变更这类动作**只给步骤与回退**，是否执行由使用者决定。
- **脱敏但保留内部标识。** 密码 / token / 证书 / 账号脱敏；集群内部标识（资源名、内网地址、ID）是检索支点，按环境口径保留。
- **素材只读。** 参考材料（排障知识库、官方文档镜像等）只读不改；引用其命令时按实际环境改命名空间 / 实例名，不照抄。
- **存量内容只追加不重排，改动要声明。** 使用者手写的既有内容不重排；超出本次范围的顺手修改（改 tags、补 frontmatter、修断链等）必须在当次操作记录里写明，不许静默修改。
- **历史档案不可改写。** 已定稿/已评审的记录（故障复盘、审计记录、决策记录）更正只以带日期的附录追加，不重写正文——改写等于伪造记录。描述性文档（讲当前机制的）相反：必须对齐现实，改了就要改准。
- **骨架空缺留占位，不删节。** 骨架里没有内容的节留 `*（……）*` 占位而不是删掉：占位是承认缺失，删节是掩盖缺失。
- **写完回读自检。** 落盘后回读刚写的文件：frontmatter / YAML 合法、每个链接的目标真实存在、没有半截代码块或未闭合表格。

## 3. 文风（标准技术中文）

### 3.1 换词

**总原则**：能用机制词就不用比喻词；省略主语 / 宾语的压缩表达，展开说。词表是示例不是穷举，未列出的按原则推导。

| 原词 | 替换 |
|---|---|
| 反直觉点 | 容易误判之处 |
| 铁证 | 直接证据 |
| member 外科手术 | 手工增删成员 |
| 故障指纹 | 稳定特征 |
| 打满 / 拉满 | 占满 / 达到上限 |
| 吞（响应/消息） | 丢弃 / 忽略（视机制） |
| 业务无感 | 业务侧无感知 |
| 暴力（删除/重启） | 强制 |
| 挂了 | 不可用 / 进程退出（视语境） |
| 搞 / 弄 | 处理 / 配置 / 执行（视语境） |
| 卡 / 卡死 | 响应缓慢 / 无响应 |
| 没事 | 无影响 / 正常 |
| 别 / 别照抄 | 不要 / 不要照抄 |
| 语气词（吧/呢/啊/呗） | 删 |

- **豁免（可用，不清洗）**：坑、兜底、上线/下线、背压、硬编码、跑（表"运行"）。
- **例外**：告警名、错误消息、日志原文、命令与代码块、术语、数字、wikilink 保留原文，不做替换。

### 3.2 换句式

换词解决不了的毛病在句式上——把词换掉、句子还是那个腔调。下表各条只给模式，出现的例句与仿写一律算命中：

| 模式 | 例子 | 改法 |
|---|---|---|
| 对偶否定（不是 X 而是 Y） | "这不是技术问题，是流程问题" | 直接给正面结论 |
| 重构式否认 | "难点从来不在配置" | 直接说难点在哪 |
| 空洞重要性宣告 | "值得注意的是""关键在于" | 说具体后果 |
| 结尾感悟句 / 收尾复述 | "这一点很重要""综上" | 删掉，停在最后一个事实上 |
| 制造洞察 | "大多数人不知道的是" | 直接给结论，不宣告它稀有 |
| 三项排比 | "更快、更稳、更安全" | 两项、四项，或那一个实测数字 |
| 铺垫句 | "下面介绍几种方式" | 直接从这件事本身说起 |
| 填充词 | "实际上""基本上""需要注意的是" | 删 |
| 虚高形容词 | 关键的、强大的、无缝的、全面的 | 换成数字、具名属性，或什么都不写 |
| 后置分词 | "……，从而提升了性能" | 删尾句，它没加事实 |
| 堆叠模糊 | "可能或许大概" | 一个断言最多一个限定词 |
| 模糊归属 | "业内认为""研究表明" | 点名来源与结论，或写明这是本人判断 |

### 3.3 两个自检（每段写完即做）

- **朗读测试**——读出声。凡不会这么对同事说的话，改写。
- **去名测试**——删掉产品/组件名再读。若看不出这段在讲什么，说明它是套话，改用本系统的具体事实重写（参考表与操作步骤不适用）。

- **结论先行，一段一义。** 每段只说一个意思，结论放段首。
- **节名即读者意图。** 每节名字回答一个读者问题（是什么 / 为什么 / 怎么认 / 怎么查 / 记哪些数 / 别做什么 / 怎么选）；不用"反模式""基线"这类行话，也不口语化；来源标注、"可直接抄"这类写作要求放节内，不进节名。

## 4. 内容完整性（一次写完，不碎片化）

同一主题的内容**一次写完、写在一处**；后续补充**回填进原位置**，不在文末另起一块。

- **同类信息只用一张表。** 同一维度（执行顺序、方案对比、环境矩阵、验收项）排在一张表里；后续新增是**加行加列**，不新开第二张——两张同维度的表会迫使读者来回对照才能读全。
- **表格不滥用。** 只在"多条 × 多个属性、且需横向对比"时上表；两列散文不是表格。结构要挣得自己的位置——有人照着它做事才值得。
- **不每段配标题**；分析类节不短于三段，更短说明它不是一个节（骨架规定的节如摘要、状态表不受此限）。
- **一次写完，不分次堆。** 首次写入就把主题写完整（含已知的后续形态与例外）；不出现"补充说明""另附""后记"式追加段落——那说明第一遍没写完。
- **分节按主题切，不按时间切。** 不出现"第一部分 / 第二部分""（上）（下）"这类按写作批次切的节；读者应能读一处得全貌。
- **补充即回填。** 主题确有演进时改写原段落 / 原表格，保持"一个主题一处正文"。允许留存时间性证据（审计日志、实测输出），但并入原位置而非另起。
- **改完要清旧。** 做替换、并段、删节时确认旧内容已删净。实测教训：patch 的 `old_string` 未覆盖全，会留下整段重复与孤儿代码块。
- **自检**：① 同一主题只出现一次；② 没有"需互相对照才能读懂"的两处；③ 无重复段落、孤立代码块、断裂编号。

判据一句话：**读者读一处就能读全，不需要"先看前面的表再看后面的表"。**

## 关联

- `k8s-obsidian-notes`：知识笔记的体裁骨架（章节结构、字段口径）与落库细则
- `writing-postmortems`：故障复盘 / 报错信号卡的体裁骨架与规则
- `obsidian-note-placement`：落点判定（项目、体裁、目录层级、查重、登记）
- `obsidian-markdown`：Obsidian 语法（wikilink / callout / frontmatter）

## 维护约定（自更新指令）

> **给后续会话：** 本文是**活文档**。一次写作中若**确证**了下列情况，按对应位置回写：

| 情况 | 回写位置 |
|---|---|
| 语言标准新增词条或豁免 | 本文 §3.1 的换词表 |
| 新确认一种句式毛病 | 本文 §3.2 的换句式表 |
| 新确认一条跨体裁写作纪律（不属于任何单一体裁） | 本文对应节 |
| 真实性 / 硬性规则有新的易错模式 | 本文 §1 或 §2 |
| 内容完整性出现新的碎片化模式 | 本文 §4 |
| 环境取值变化（库路径、落点惯例、命名） | **本文不动**，回写对应体裁 skill 的 `references/local-adaptation.md` |
| agent 通道或能力变化（新工具、新限制） | **本文不动**，回写对应体裁 skill 的 `references/harness.md` |

### 规则本身的生长规则

- 新规则要记下**触发它的事件**（什么情况、谁提的、何时加的、例子），便于日后判断是否还成立。
- 同一个错误**发生两次**才立规则；一次只是学习，不急着写进去。
- 反复触发的规则要打磨**触发条件**（更明确的判据、例子）；根因已修的规则及时退役。"小心点"不是规则。
- 例外写在它豁免的那条规则旁边，不只写在用到它的那份文档里。

只记确证的，不记推测；改动从真源发起再分发。执行中若顺手调整了规则之外的**存量内容**，必须在当次操作记录里声明，不许静默修改。
