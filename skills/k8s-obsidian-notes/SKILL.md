# 知识笔记（k8s-obsidian-notes）

**前置要求：** 写作纪律以 skill `technical-writing` 为准（真实性规则、硬性规则、文风、内容完整性）——**本文 §4 与「规则」节保留一份内联副本作兜底**，两者不一致时以 `technical-writing` 为准。Obsidian 语法见下文「Obsidian 语法最小集」节（**本文件自带，不依赖外部 skill**；扩展语法可参照可选的 `obsidian-markdown`）。索引/日志维护、互链铁律、完成前自检等机制内联在本文与适配层，不依赖外部 skill。

> **本 skill 分两层**：① 通用层（本文）——笔记骨架、字段语义、写作姿态与规则，跨环境可用，不出现具体路径、库名或工具名；② 本地适配层（`references/`）——`local-adaptation.md` 记**环境事实**（库路径、落点、frontmatter 取值、索引登记、素材源；各运行环境下应逐字节一致），`harness.md` 记**本 agent 的写入通道与能力限制**。**换项目或换库时，替换 `local-adaptation.md` 即可，通用层不动。** 适配层不存在时，按通用层自带的语义描述执行。

## 0. 一句话

读文档/代码，或拿到排障结论 → **先定落点** → 按模板提炼机制、数字与决策 → 写入文档库 → 登记索引与日志 → 与相关笔记互链。

**目标**：让读者能迅速找到结论、判断依据和可执行命令。只覆盖本篇声明的问题所需的信息，不为凑齐维度扩写；保留证据及其确定性，摘要、索引和关联说明不得比原文更肯定。

**范围边界**：故障文档（复盘骨架、告警与标志性日志、时间线、恢复步骤、行动项）由 `writing-postmortems` 定义，本 skill 不重复其模板。知识笔记不重复故障细节，只留**可复用的机制、数字与决策**。

## 1. 先读什么（动手前必读，按顺序）

1. **落点** — 先走 skill `obsidian-note-placement`：项目、体裁、目录层级以文档库内的「归类总表」为准。本 skill 只定"怎么写"，不定"放哪"。
2. **同主题笔记** — 目标主题目录下是否已有可更新的笔记（决定新建、更新、拆分还是合并，见 §5）。
3. **素材源** — 只读素材库（若有）的路径见适配层 §5；引用其中的命令时按实际环境改命名空间/实例名，勿照抄。

## 2. 骨架

按读者要解决的问题组织内容，不要求每篇都包含下面所有章节。机制类笔记通常用「概述 → 工作原理 → 异常识别 → 命令/数值 → 决策」；速查类以「概述 → 命令或对照表 → 验证与注意事项」为主。没有实际内容的章节直接省略，不写占位。

````markdown
---
tags: [<库知识类标签>, <主题>]        # 取值见适配层
category: concept                    # 取值与在用分类见适配层；你的库若不用分类维度，删掉这一行
summary: <一句话概述；必填，自动索引的摘要来源>   # 缺它时索引回退显示正文首行，故 H1 后首行也写人话
sources: <支撑本页的来源数；可选>
origin: local                        # 来源分级；取值与缺省后果见 §3，用按来源分级的索引工具时才需要
updated: <YYYY-MM-DD；每次编辑更新>
title: <与 H1 一致>
---

# <标题：机制名或组件名 + 简述，名词短语，不用日期前缀>

## 概述
- 一句话定义 + 它在生产里解决什么问题（可用性/容量/安全/成本哪一环）

## 工作原理        # 速查/命令类（category: handbook）可整节不建，不留占位
- 机制，按"为什么"组织；配图用 mermaid
- 关键结论标注来源：[[相关笔记]] / 官方文档 / 实测
- 版本间行为差异（内容少时写在这里；≥3 条可独立成「版本差异」节）

## 运行表现与异常识别
- 识别向：生产中的真实输出、报错原文、日志片段
- 正常 vs 异常的判断线（什么输出算正常，什么算坏）

## 常用命令
- 可直接抄的完整命令，注明验证环境（版本/部署形态）与需按实际替换的部分

## 关键数值
- 容量/超时/频率等经验值，写数字不写形容词；每条标注来源：**实测** / **经验** / **官方**

## 常见问题与错误做法
- 规避向。坑：现象 → 原因 → 规避；错误做法：看似合理但在生产环境会引发故障的操作

## 取舍与决策
- 场景 → 建议；可用性 / 容量 / 安全 / 成本四象限的权衡

## 关联
- [[相关笔记]]：关系一句话
````

**概述与关联按需保留，其余章节按素材选用。** 没有「关键数值」「取舍与决策」或异常识别内容时不建对应章节，也不写「暂无」占位。「版本差异」不足 3 条并入相关节；速查/命令类笔记（`category: handbook`）不要求「工作原理」节。完整性指读者能回答本篇的问题，不是凑齐八个维度。

**分节界限（易混两处）**：「运行表现与异常识别」管**识别**（帮你认出来），「常见问题与错误做法」管**规避**（帮你别掉进去）——报错原文、判断线放前者；错误操作、踩坑教训放后者。

## Obsidian 语法最小集（写笔记够用的那部分）

本方案自带的语法子集——写这类笔记只需要这些；`obsidian-markdown`（可选外部 skill）只用于查扩展语法，装没装都不影响执行。

- **链接**：库内用 `[[文件名]]`（不带路径、不带 `.md`，按文件名解析——**写后必须核对目标文件名**）；要显示文本时 `[[文件名|显示文本]]`；外部链接用 `[text](url)`。
- **附件与配图**：`![[文件名.png]]`；需要控制宽度时 `![[文件名.png|600]]`。
- **强调块**：`> [!info] 标题`、`> [!warning] 标题`——callout 是独立语法，与普通引用块 `> ` 不同。
- **流程 / 架构图**：`` ```mermaid `` 代码块。
- **行内高亮**：`==要点==`（低频，不用也成立）。

以下语法在本库笔记里没有用过，**默认不引入**：数学公式、脚注、块引用 `^block-id`、`aliases` / `cssclasses` 等扩展 properties。确有需要时查 Obsidian 官方文档或可选的 `obsidian-markdown`。

## 3. 字段口径（语义约定，不含具体值）

- **标题**：机制名或组件名 + 简述，简短名词短语，不用日期前缀（与故障文档的日期前缀区分体裁）。
- **概述**：一句话定义 + 生产价值定位，两段内说完。
- **category**：`concept`（机制/原理）· `handbook`（可抄的命令与参数速查）· `comparison`（对比）· `synthesis`（综述）。**哪几类在用，以适配层和各项目索引页列出的分类表为准**，新笔记优先在在用分类里选，不要为了凑分类新开一张表；`comparison` / `synthesis` 仅在确实成篇对比或综述时才用。
- **summary**：必填，供自动索引和检索速览，通常约 120 字，只写对象、核心结论和必要限制。不要塞入完整过程、全部数值或全部行动项。正文首段另交代背景和主线，不复述摘要。缺了会回退显示**正文首行**，所以正文首行也别以 `## 节名` 开头。
- **来源标注**：经验性断言强制标注 **实测**（本环境验证过）/ **经验**（行业惯例）/ **官方**（文档数值）；数字优先于形容词。
- **来源分级 `origin`**（用按来源分级的索引工具时才需要）：本地实测或使用者确认过的写 `local`；外部资料写 `web`；自行推理、未经验证的写 `inferred`。**字段缺失时工具默认按 `local` 处理**，外部内容会混进"已验证"检索结果——引用外部结论的笔记必须显式标注；取值与缺省后果见适配层。
- **关联**：只链真实存在且有助于理解或操作的笔记；没有合适目标就不建本节，不为互链创建空 stub。
- **节名即读者意图**：每节名字回答一个读者问题（是什么/为什么/怎么认/怎么查/记哪些数/别做什么/怎么选）；用词以"能看懂"为准——不用"反模式""基线"这类行话，也不口语化；来源标注、"可直接抄"等写作要求放节内，不进节名。
- **版本差异**：内容 <3 条并入「工作原理」或「常用命令」的验证环境说明，≥3 条才独立成节。

具体取值（库路径、tags、主题清单、在用分类、示例）放适配层，不放这里——通用层一旦写死具体值，换环境就废。

## 4. 写作姿态与语言标准

> 正本在 `technical-writing`：§1 真实性、§2 硬性规则、§3 文风（换词表与换句式表）。**写知识笔记时该 skill 必读**；下面只留四条最要紧的兜底，以及本 skill 特有的写作要求。

**四条兜底**（正本未加载时守这几条）：
1. **不编造**，不确定写"待确认"并注明来源；信息不全先一次问清，不边写边猜。
2. **结论先行，一段一义**；每条断言可验证，数字优先于形容词。
3. **命令是给以后的人抄的**：完整、参数真实、注明版本差异与执行位置。
4. **写完回读**：见 §6。

**本 skill 特有的写作要求**：

- 涉及上线/变更的笔记用 checklist（上线前检查/故障前检查）。
- 提及的重要组件/概念要给 wikilink，**链接位置按该库的链接惯例**：库的惯例是"文末「关联」节集中列"就放那里，是"正文内嵌"就内嵌——位置以适配层为准，本层不规定。默认按文末「关联」节处理。
- 从故障复盘提炼时，先分三栏：**已确认的通用机制、只在本现场成立的实测值、仍待确认的推测**。只把前两类写进机制正文，第三类保留限定或留在复盘，不得进入摘要、索引和通用决策建议。没有新增证据时，任何转述都不能比原复盘更确定。
- 知识笔记只保留理解机制所需的最小现场证据，链接回复盘获取时间线、Pod 名和恢复过程；不要复制整段事故经过。现场数值与通用建议分开，单个案例不直接改写成所有环境的判据。
- **日志按判断依据高亮。** 在错误日志、正常/异常输出或事件片段中，直接突出支持本节判断的字段：错误码、退出原因、资源名、阈值、实际值及恢复结果。不要把所有数字都染色，也不要只在块后另写解释而省略正文强调。使用与故障复盘一致的颜色语义和本库 class，让读者反复看到相同字段时形成定位习惯；写后检查实际渲染和复制结果。
- **内容完整性**：同一主题一次写完、写在一处；同类信息只用一张表（后续新增是加行加列，不新开第二张）；补充回填进原位置，不在文末另起；不按写作批次分节。

## 5. 落地工作流

1. **定落点** — 走 skill `obsidian-note-placement`（项目 / 体裁 / 目录层级）。
2. **查重** — 目标目录有同主题笔记时：是它的延续 → 更新原笔记；是不同侧面 → 新建并互链；结论与之矛盾 → 先核实再改，不让两份冲突结论并存。描述性笔记需要重排、压缩或全文重写时，先取得使用者明确要求；更新不得靠文末追加形成第二份正文。
3. **写** — 按 §2 骨架、§3 字段口径、§4 写作姿态与语言标准。
4. **落盘** — 直接写目标路径，不走收件箱待审中转；新建目录时登记项目内分类表，并按适配层要求做目录配套动作。
5. **互链** — 有真实目标时，按该库的链接惯例组织链接：① 来源故障文档；② 相关主题笔记。库支持 wikilink 就用 wikilink（按文件名解析，链接后必须核对目标文件名）。来源故障文档的「关联」节补回链；若该复盘已定稿或已评审，回链只写进它允许单独更新的区域或附录，不改叙事正文。没有可链目标时不建该节，不创建空 stub。
6. **登记** — 自动维护的索引（工具扫描生成）**不要手改**；手维护的索引/日志**写完即登记**，不等"成体系"。落点对应哪些登记点、行格式是什么：按 skill `obsidian-note-placement` 的登记对照表，加上本 skill 适配层 §3 的行格式。
7. **自检** — 见 §6；发现问题当场修掉，不要留给下一个人。
8. **汇报** — 落点、新增/更新、登记点、遗留待确认项。

## 6. 回读自检（写完不算完）

通用项（frontmatter 是合法 YAML、每个 wikilink 目标真实存在、无半截代码块或未闭合表格）按 `technical-writing` §2 硬性规则中的「写完回读自检」条执行。

知识笔记特有的，逐条过：

- 每节都回答一个实际问题；没有空节、为凑齐骨架添加的内容或重复事故现场；
- 「关键数值」每条都标了来源（实测 / 经验 / 官方），没有裸给数字；
- 摘要、正文、索引与关联说明保留了原复盘的证据等级，待确认内容没有被改写成确定结论；
- 有来源故障文档时，其允许的「关联」区域已补回链；没有真实链接目标时不建空节或空笔记；
- 引用的日志正文已突出支持判断的字段，颜色语义与故障复盘一致；实际阅读视图和复制结果已验证。

## 7. 触发场景 / 不适用

**触发**：用户说"沉淀知识""写知识笔记""整理笔记""整理到 obsidian"；读文档/代码或拿到排障结论后要固化机制、数字与决策。

**不适用**：故障复盘、事故报告、复盘归档 → `writing-postmortems`；报错信号卡 → `writing-postmortems` §3.2；"这篇放哪""整理 Inbox""目录结构合不合理" → `obsidian-note-placement`。

## 本环境适配

见 `references/` 下两个文件：`local-adaptation.md` = **环境事实**（库路径、落点与命名、frontmatter 取值、在用分类、索引/日志登记格式、素材源）；`harness.md` = **本 agent 的写入通道与能力限制**。

**迁移约定**：换项目、换库或换工作时，只替换 `local-adaptation.md`（或删掉它，退化为纯通用骨架）；本文的骨架、字段语义、规则一律不动。

## 规则

> 通用写作纪律（不编造、命令可复制、脱敏、素材只读、按文档状态修改、章节按需省略、写完回读）以 `technical-writing` 为准；下面只列本 skill 特有的。

- **只写文档库。** 不改代码仓库、不动集群状态、不替使用者执行变更。
- **按文档状态修改。** 使用者要求保留的手写内容默认只追加；描述性笔记在使用者明确要求时可重排、压缩或全文重写；已评审历史档案仍只追加更正。
- **敏感值脱敏，内部标识保留。** 密码/token/证书/账号脱敏；集群内部标识（ID、资源名、内网地址）是检索支点，按适配层口径保留。

## 维护约定（自更新指令）

> **给后续会话：** 本 skill 与两份适配层都是**活文档**。在一次写作中若**确证**了下列情况，按对应位置回写：

| 情况 | 回写位置 |
|---|---|
| 用户纠正骨架（节名、必填节、占位规则） | 本文 §2 / §3 |
| 语言标准新增词条或豁免 | **本文不动**，改 `technical-writing` §3.1 正本 |
| 通用写作纪律变化（真实性、命令纪律、内容完整性等跨体裁规则） | **本文不动**，改 `technical-writing` 正本；仅当属于「四条兜底」范围内的变化，才同步本文 §4 |
| 用户取消/新增某个字段口径（如严重级、category 枚举、origin 来源分级） | 本文 §3 |
| 环境取值变化（库路径、落点惯例、tags、在用分类、索引登记点、素材源） | `references/local-adaptation.md` |
| agent 通道或能力变化（新工具、新限制） | `references/harness.md` |
| 判定规则本身需要修正（新的易错模式） | 本文对应节（只写通用规则，不写环境值） |

只记确证的，不记推测；改动从真源发起再分发（见适配层开头的"真源与分发"）。执行中若顺手调整了规则之外的**存量内容**（改 tags、补 frontmatter、修断链等），必须在当次操作记录里声明，不许静默修改。
