# 故障文档（writing-postmortems）

**前置要求：** 上游 `technical-writing` skill（硬性规则、真实性规则、文风）。本环境未安装，直接按下文规则执行。

> **本 skill 分两层**：① 通用层（本文）——骨架、字段语义、写作规则，跨技术栈/跨组织可用，不出现具体集群名、命名空间或产品名；② 本地适配层（`references/`）——`local-adaptation.md` 记**环境事实**（落库路径、落点、frontmatter 取值、索引登记、证据命令；所有运行环境下应当逐字节一致），`harness.md` 记**本 agent 的写入通道与能力限制**（各运行环境可能不同）。**换项目或换工作时，替换 `local-adaptation.md` 即可，通用层不动。** 适配层不存在时，按通用层自带的语义描述执行。

## 0. 一句话

故障处置结束后，把**证据**（时间线、报错原文、告警）与**机制**（根因、诱因）写成一年后还能被搜到、被复用的档案，并提炼出带负责人与验收标准的行动项。

**输出语言：默认中文**（除非用户另有指定）；命令、代码、日志原文保持逐字原样。

**两种体裁，不要混用骨架**：

| 体裁 | 识别特征 | 骨架 |
|---|---|---|
| 完整复盘 | 有故障窗口、影响、时间线、根因 | §3.1 |
| 报错信号卡 | 一条报错原文 → 快速判定，篇幅短、可独立检索 | §3.2 |

## 1. 定位与适用范围

读者是一年后撞上类似问题的工程师，不是当时在场的人。核心原则：**事实来自证据，原因来自机制，教训来自两者，不出现人名。** 文档归类为历史档案：评审后即固化，更正以带日期的附录追加。

固定链路：**使用者报故障 → 就地排查、给可执行步骤（这一步不写文档）→ 使用者执行恢复 → 使用者要求后写故障文档**。不要越位：故障还在进行时写文档，会让排查分心。

故障解决后调用；长故障在稳定里程碑处也可以成文。波及用户的缺陷与未遂事故（护栏抓住了评审漏掉的东西）同样值得写。

什么时候**不该**用本 skill（含"故障进行中不写"这条）见 §8。

## 2. 写前信息清单（缺什么就问什么）

动笔前先对着这张清单自查，**缺的项一次性列出来向使用者提问**，不要带着空白开始写、也不要边写边猜：

| 项 | 要拿到的东西 |
|---|---|
| 故障窗口 | 起始时间、发现时间、恢复时间（精确到分钟，取自系统而非记忆） |
| 环境与组件 | 环境标识（哪个部署/集群/租户）；范围（命名空间/模块）；组件全名与版本；副本数或实例数 |
| 现象与报错 | 报错原文（逐字，含关键 ID：各类唯一标识符、资源名、请求 ID） |
| 告警 | 哪条规则触发、告警内容原文；没有告警就明确"无告警触发，由 X 发现" |
| 影响 | 谁受影响、量化（失败请求数、受影响记录数、不可用时长）；未检查过数据丢失就不要下结论 |
| 排查过程 | 按序的检查动作 + 发现 + 推断，含被排除的假设 |
| 恢复动作 | 确切命令 / 配置变更 / 数据修复；每步的验证方式；危险步骤的回退 |
| 根因 | 机制层面的解释；诱因；哪一层检查漏掉了它 |
| 弯路 | 走错的第一步、被误导的信号、错误的假设 |
| 当前状态 | 已恢复 / 待执行 / 部分恢复 |

使用者答不上来的项（尤其历史时点、旧操作记录）：写"未记录"或"未知（推算）"并注明来源，**不要为了让文档好看而补一个像样的答案**。

**信号卡的信息量小得多**：报错原文（逐字）、判定结论（含"不是什么"）、机制一句话、处置命令、验证方式。同样不许用推测补空——**判不出根因就写"机制待确认"并注明已排除的方向**，不要给一个像样的错根因（信号卡是被高频引用的速查物，错根因危害大于缺失）。

## 3. 骨架

### 3.1 完整复盘

````markdown
# <组件/对象> <症状>（<环境标识>）

| | |
|---|---|
| **日期 Incident date** | YYYY-MM-DD（发现）；YYYY-MM-DD 修复 |
| **环境 Environment** | <环境标识>（<范围 / 组件 + 版本>） |
| **时长 Duration** | 从发现到恢复；未恢复则写"未恢复；已持续 <时长>" |
| **状态 Status** | 草稿（未评审）/ 草稿（根因已定位，方案待执行）/ 已评审 |

## 摘要 Summary
[现象（带数字、带报错原文）+ 根因一句话 + 当前状态。只读这一段也要知道发生了什么。]

## 影响 Impact
[谁、什么受影响，量化：失败请求、受影响记录、损失时间。
估算要标注为估算；"未发现数据丢失"只有在真正检查过、并写明检查范围后才能写。
原始记录确实没有影响信息时写一行 `*（原始记录未单列影响…）*`，不要编。]

## 告警与标志性日志 Trigger and signature evidence
**告警原因**：[触发的告警规则名/阈值/内容原文；本应触发却缺失的，缺失本身就是发现；无告警时如实写"无告警触发，由 … 发现"]

**标志性日志（逐字引用）**：

```text
<能识别本次故障形态的报错原文；敏感值脱敏；不转述改写。排查中的弯路、工具自身报错、被排除方向的报错放「响应中的弯路」节，不放这里>
```

**症状识别**：

| # | 症状 | 检测方法 | 置信度 | 排除条件 |
|---|------|---------|--------|---------|
| S1 | <现象> | <命令 / 日志来源> | 0.9 | <什么情况下不是它> |

目标：下次有人拿这些关键字搜索时，能命中这份文档。

## 时间线 Timeline
[带时间戳的事实条目，每条可追溯到证据：一条告警、一行日志、一个提交、一条消息。解读不要混进时间线。]

### 排查与推断（原记录未逐条带时间戳）
[原始记录没有时间戳时，排查过程按序放这里，保留这个小标题——它明确声明"以下不是时间线"。]

## 恢复步骤 Recovery
[让服务恢复的确切动作，按顺序、可复制：命令、配置变更、数据修复、重启/切流等。
与"响应弯路"和"行动项"区分：本节只写当时实际走通的那条路。]

### 验证
[逐条核对，全部通过才算恢复：命令 + 期望输出/现象。危险步骤写明回退与注意事项。]

## 根因与诱因 Root cause and contributing factors
[机制层面的解释，落到代码与提交上；诱因单列。
"每个组件都正确、缺陷活在组件之间"是合法的根因。
写明哪一层检查漏掉了它、哪一层抓住了它。]

## 响应中的弯路 Wrong turns during the response
[走错的第一步、被误导的信号、花掉一小时的错误假设。当时的推理也要留下——那是后来人能理解"为什么会这么想"的凭据。]

## 行动项 Action items
[每项带负责角色与验收标准；没有负责人的"调查 X"在这里和别处都被禁止。
不接工单系统时，行动项以本文档为终态，不要求外链工单。]

## 总结 Lessons learned
[经验教训，控制在三五条：本次响应做得好的、做得差的、下次会不同做的。
总结是判断，行动项是承诺；此处不复述行动项清单。]

## 签核 Sign-off
[- YYYY-MM-DD <评审人>：批准 <范围>，每次评审一行。]

## 关联
[链到从本次故障提炼出的知识笔记与相关故障文档；只链真实存在的笔记；无目标就不建此节。]
````

**定稿后只加附录**：`## 附：<日期> <内容>`（后续同类案例、补充抓证、复核结论）。追加不改正文——那才是"历史档案"该有的样子。

**骨架里没有内容的节，用一行占位标注而不是删掉**：`*（原始记录未单列…）*`。占位是"有意识地承认缺失"，删节是"掩盖缺失"，一年后读的人分不清是真没有还是没写。

**「标志性日志」只收表征本次故障形态的原文**：排查中被排除方向的报错、工具自身报错（如 curl 的协议错配）、环境侧无关报错放「响应中的弯路」——否则别人拿这串关键字搜到本复盘，却发现与主根因无关。

### 3.2 报错信号卡

信号卡是**速查物**，不是缩小的复盘：它回答"看到这行报错，先往哪想"。骨架自现有卡片归纳，**不要套用 §3.1 的复盘骨架**。

````markdown
---
tags: [<库故障类标签>, <信号卡分类标签>, <组件或信号类别>]
trigger_keywords: ["<报错原文短语>", "<唯一标识>", "<现象词>"]
title: "<报错原文> —— <一句话判定>"     # 含冒号/引号时必须用双引号包住整个值
summary: <一句话：什么信号 → 是什么问题 → 处置方向>   # 缺它时索引回退显示正文首行，故 H1 后首行也写人话
---

# <报错原文> —— <一句话判定>

> 报错信号：`<报错原文，逐字，含关键标识>`
> 快速判定：**<一眼结论；点明"不是什么"，防止往错方向排查>**
> 关联：<同类信号卡或故障复盘>、<机制知识笔记>

## 信号特征

- <2 条以内，写"为什么是它 / 为什么不是别的"，给判断线而不是现象罗列>

## 根因机制

- <机制层面讲透；判定依据能站住的原因就在这里。非实测的机制解释要标来源，见 §4>

## 处置

```bash
# <按序、可复制；标注执行位置（哪台机器/是否容器内）；需按实际替换的部分标出来>
```

> [!warning]
> <危险步骤、易踩的坑、回退方式。没有就删掉这一段 callout。>

## 验证

- <命令 + 期望现象，逐条可核对>

## 姊妹信号

- <同类但不同根因的信号 → 指向哪张卡；没有就删掉本节>

## 现场（<YYYY-MM-DD>）

- <本机真实环境值。可选节：只在有真实现场时写，没有就删掉>
````

固定节与可选节：`信号特征 / 根因机制 / 处置 / 验证 / 姊妹信号` 五节为固定节（姊妹信号确实没有同类信号时删）；顶部三行引言块**不可省**——它是"看到报错原文即可定位"的载体，也是所在目录速查/登记表的字段来源（该表是否存在、叫什么，见适配层）。`## 现场` 与 `> [!warning]` 为可选：**`## 现场` 只在两种情况写**——① 同一报错在不同环境下的根因或处置不同（现场用来区分形态）；② 需要标明首次观察到它的具体环境以便追溯；其余情况删掉，"哪次故障里出现"属于对应复盘的职责。`> [!warning]` 在有危险步骤或易踩的坑时写（也可内联进「处置」）；两者都没有就删掉，不要写占位。

**同一张卡只解决一个信号**：一张卡塞两种报错，检索时两边都命中不准。相关的第二、第三个信号写进「姊妹信号」并另建卡。

## 4. 字段口径（语义约定，不含具体值）

- **H1**：完整复盘用 `# <组件/对象> <症状>（<环境标识>）`，一行说清"什么东西坏了 + 什么症状 + 在哪"；信号卡用 `# <报错原文> —— <一句话判定>`，` —— ` 两侧各留一个空格。**不要用 `系统: 故障` 这类冒号式标题。**
- **环境标识**：这个部署在那个组织里的叫法——集群名、环境名、产品线、租户，怎么叫都行，但**必须出现在元信息表里**（不能只写在标题）。它是跨环境检索的唯一抓手：一年后别人问"别的环境有没有同类问题"，靠它筛。
- **范围 / 组件 + 版本**：命名空间或模块 + 组件全名 + 版本号，能定位到具体工作负载即可。
- **日期**：`YYYY-MM-DD（发现）；YYYY-MM-DD 修复`；两者同日就写一个。
- **状态**：`草稿（未评审）` / `草稿（根因已定位，方案待执行）` / `已评审`。未评审就是草稿，这是正常状态，不是缺陷。
- **时长 Duration**：从发现到恢复；未恢复写 `未恢复；已持续 <时长>`。
- **机制的来源**：信号卡的「根因机制」节若写的是通用技术常识（协议栈行为、内核机制、组件实现等）而非本次现场实测，**必须标注来源**（官方 / 实测 / 经验）；确认不了的写"机制待确认"并列出已排除的方向。速查物被高频引用，错根因比缺根因危害大。

具体到某个项目的字段写法（含目录、tags、示例值）放适配层，不放这里——通用层一旦写死具体值，换环境就废。

## 5. 命名与 frontmatter（落库时）

不落库的复盘只按上文骨架输出。落进文档库时，骨架之外**必须**带 frontmatter 封装，否则检索与索引丢字段。

- **文件命名**：`<YYYY-MM-DD>-<简述>.md`。完整复盘用发现日（与 §4 的日期口径一致）；**信号卡用该信号首次被观察到的现场日期**——同一信号在多处出现取最早那次，事后归纳、无单一现场的用成文日，并在「现场」节写明"无单一现场"。简述用故障症状短语（信号卡用报错短语）。
- **落点目录**：**不写死**——先走 skill `obsidian-note-placement` 定项目与目录层级；目录不存在就新建。
- **frontmatter 必备键**：
  - 两种体裁共同：`title`（与 H1 一致）、`tags`（含文档库的故障类标签 + 组件/主题标签）、`trigger_keywords`、`summary`（**必填**，一句话；它是工具自动生成的索引页的摘要来源，缺了那一页回退显示**正文首行**——正文别以 `## 节名` 开头，否则摘要退化成零信息词）。
  - 完整复盘另加：`estimated_resolution_time`（实际耗时；未恢复时如实写"未恢复（截至 <日期> <进展>）"）。
- **trigger_keywords 选词规则**：报错/告警原文的关键短语逐字收录；唯一标识符（各类 ID、资源名）；故障现象词。目标：下次有人拿现场关键字搜索时能命中本文。
- **YAML 引号规则**：frontmatter 取值含 YAML 特殊字符（半角冒号 + 空格、空格 + 井号等）时**整值加双引号**——YAML 不报错，但会静默截断或把值解析成嵌套结构。本条与语言、环境无关。
- **写入通道**：优先用文档库原生的写入方式（文件写入工具写绝对路径，或该库的 MCP 工具改 frontmatter / 正文片段）；只有目标确实不可写时，才退化为"先在可写位置生成完整文件、再复制覆盖"。

## 6. 落地工作流

1. **定体裁** — 完整复盘还是信号卡（§0 的表）。
2. **收证据** — 按 §2 清单收集；缺项一次性问清。
3. **定落点** — 走 skill `obsidian-note-placement`（项目 / 体裁 / 目录层级 / 查重）。
4. **写** — 按 §3 对应骨架、§4 字段口径、规则。
5. **落盘** — 直接写目标路径，不走收件箱待审中转；新建目录时登记项目内分类表，并按适配层要求做目录配套动作。
6. **互链（必做）** — 文档末尾加/保留「## 关联」节，链两类目标：① 从本次故障提炼出的知识笔记；② 相关故障文档（同环境复发、同机制的其他环境）。有该库的 wikilink 语法就用它，没有就用普通链接。只链**真实存在**的笔记：目标不存在就是死链——先建 stub 或写「（待建）」，不要留悬空链接。同名冲突时写全路径。**反向也要接**：对应知识笔记的「关联」节注明来源故障文档，形成双向；单向链接等于半成品。确实没有可链目标时不建该节，不硬凑。
7. **登记** — 自动维护的索引（由工具扫描目录生成）**不要手改**，让工具刷新；手维护的索引/目录页**文档写完即登记**，不等评审——索引的价值是"能被搜到"，不是"评审通过"。落点对应哪些登记点、行格式是什么：按 skill `obsidian-note-placement` 的登记对照表，加上本 skill 适配层 §3。
8. **自检** — 见 §7；发现问题当场修掉，不要留给下一个人。
9. **汇报** — 落点、体裁、登记点、遗留待确认项。

## 7. 回读自检（写完不算完）

写盘后回读一遍刚写的文件，核对三项——① frontmatter 键完整、YAML 合法；② 每个 wikilink 的目标文件**真实存在**（按文件名逐个核对，不凭印象）；③ 没有半截代码块或未闭合的表格。

## 8. 触发场景 / 不适用

**触发**：故障/事故/缺陷/未遂事故处置结束后要成文；把故障群、告警日志、值班记录整理成长期文档；给已有故障补一张报错信号卡。

**不适用**：故障进行中的响应指挥（那时由 runbook 指挥，见 §1 的固定链路）；给相关方的状态通报（那是报告，不是复盘）；用于追责（一份需要人名才讲得通的复盘，描述的是流程漏洞）；知识笔记 → `k8s-obsidian-notes`；"这篇放哪""整理 Inbox" → `obsidian-note-placement`。

## 本环境适配

见 `references/` 下两个文件：`local-adaptation.md` = **环境事实**（落库路径与目录约定、tags 取值、索引登记格式与位置、当前技术栈的证据收集命令、本机排障知识库路径）；`harness.md` = **本 agent 的写入通道与能力限制**。

**迁移约定**：换项目、换技术栈或换工作时，只替换该文件（或删掉它，退化为纯通用骨架）；本文的骨架、字段语义、规则一律不动。

## 规则

- **信息不全就先问，不许编。** 写文档时缺时间、报错原文、影响范围、恢复动作、根因等任何一项，**先向使用者一次性列出缺失项并提问**；使用者答不出的，写"未记录 / 未知（推算）"并注明来源。**禁止用合理推测填充正文**——一份编得像样的复盘，比一份承认"未记录"的复盘危害大得多，因为后者会被追问，前者会被当成事实引用。
- **对事不对人，落在结构上。** 点名角色、关卡、依赖、缺失的护栏，绝不点名个人。归咎于个人只能得到"以后小心点"，归咎于结构才能产出行动项。这条约束叙事部分（时间线、根因、响应过程）；行动项的负责人是任务分派，不是追责：本文档里写角色，具体人名不入档。
- **时间线是证据，不是叙事。** 每条都可追溯到可核查的东西，时间戳取自系统而非记忆。若唯一来源是记忆，明确写出来。
- **走错的修复也是正文。** 当时合理但没生效的修复，连同当时让它显得合理的推理一起写进文档；难堪不是删除理由。
- **不设严重级**（除非使用者所在组织已有明确定义的分级体系，则用其分级并要求同时给出判据）。默认不要在文档里引入自创等级；需要表达轻重时，在摘要里直接写可感知后果。
- **骨架里没有内容的节，留占位标注不删节**（`*（原始记录未单列…）*`）。占位 = 承认缺失，删节 = 掩盖缺失。信号卡的可选节（现场、warning）例外：没有真实内容就删掉，不写占位。
- **行动项落到"谁做 + 验收标准"**，不以散文意图的形式留在复盘里。组织暂无工单系统时，行动项在本文档内即为终态，写负责角色，不因缺链接而卡在草稿；接入工单后，再把每项替换为工单链接。
- **评审闭环**：有第二评审人时由其签核；单人环境（没有第二人可评审）则评审人即使用者本人，评审后记一行签核、把状态由"草稿（未评审）"改为"已评审"；未评审的文档保持草稿状态，这属于正常状态，不是缺陷。
- **定稿后只加附录，不改正文。** 新发现写成 `## 附：<日期> <内容>`；重写已评审的复盘等于伪造记录。评审本身记为一行签核。
- **未遂事故用同一套骨架**，影响一节描述"本会发生什么"，并明确标注这是反事实推演。
- **恢复步骤要可复制。** 写给"一年后照着做"的人：确切命令与配置差异，不写"重新部署一下"这类转述；每步给出验证方式；危险步骤写明回退。
- **命令要写明执行位置，高风险动作不代执行。** 给使用者的每条命令都标出**在哪台机器 / 哪个环境 / 是否容器内**执行，不要把执行位置留给读者猜；删除数据、缩副本、重启生产组件、批量变更这类高风险动作**只给步骤与回退**，是否执行由使用者决定。远端命令的预期输出不得写成已验证结果。
- **标志性日志逐字引用。** 报错、错误码、关键输出保持原文（敏感值按组织要求脱敏），不转述改写。
- **语言标准。** 中文行文用机制词替代比喻词，不用口语化或比喻表达（省略主语/宾语的压缩表达要展开）。**同环境若装了 `k8s-obsidian-notes`，以它通用层 §4.2 的「语言标准」节为准**——完整替换表、豁免词与例外清单都在那里；未装时按本条原则自行推导。故障文档的标志性日志、告警原文逐字引用，属例外，不做替换。

（上游同系列 skill：`technical-writing`、`writing-issues`、`recording-decisions`、`writing-runbooks`——本环境均未安装，按上述规则执行即可；复盘之后常伴随的决策与新不变量归 `recording-decisions`、故障暴露的 runbook 更新归 `writing-runbooks`，都不嵌在复盘里。）
