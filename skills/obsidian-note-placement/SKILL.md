# 笔记归类落地（obsidian-note-placement）

> **本 skill 分两层**：① 通用层（本文）——判定流程、规则、工作流与自检，不出现具体路径、项目名或工具名；② 本地适配层（`references/`）——`local-adaptation.md` 记**环境事实**（文档库在哪、归类总表在哪、各项目的分类表与登记点、移动笔记的本机做法），`harness.md` 记**本 agent 的写入通道与能力限制**。
>
> **归类规则本身（项目边界、体裁表、命名对照、裁决先例）存放在文档库内的「归类总表」里**，所有 agent 共读、随文档库一起维护。本 skill 不复制这份表，只规定怎么用它、什么时候更新它——这样规则只有一处，不会在多个 skill 之间漂移。

## 0. 一句话

写之前先定"放哪"：读归类总表 → 按**内容主语**定项目 → 按**体裁**定命名与写作规范 → 按**涉及范围**定目录层级 → 查重 → 落盘、登记、做目录配套动作 → 回读自检 → 出现新边界时回写归类总表。

## 1. 先读什么（动手前必读，按顺序）

1. **归类总表**（文档库根）：每个一级项目收什么、不收什么；体裁表；命名对照；裁决先例。
2. **项目内分类表**（目标项目的索引页）：项目下有哪些子目录、各收什么、命名规则、登记点。
3. **目标目录现状**（自动索引或直接列目录）：有没有同主题笔记、现有文件名是什么风格。

三者缺一不可。**以文档库当前状态为准，不凭记忆**：本 skill、写作 skill 或记忆里的落点描述与库内现状冲突时，以库内为准，并提示修正过时的那一份。

**归类总表不存在时，先建它再归类**：本 skill 假设库里已有一份归类总表。遇到没有总表的库（新库、刚从别处迁移过来的库），先与用户一起建立一份最小总表——至少含一级项目的边界（各收什么 / 不收什么）与体裁表，然后才开始判定；不要把项目边界临时写进本 skill，也不要凭记忆判。

## 2. 三步判定

| 步 | 要回答的问题 | 决定什么 | 依据 |
|---|---|---|---|
| ① 项目 | 这篇讲的是**什么系统 / 对象**？ | 一级目录 | 归类总表·项目边界 |
| ② 体裁 | 这是**哪种文档**？（机制说明 / 故障复盘 / 报错信号卡 / 升级记录 / 同步裁决 / 巡检记录 / 操作记录 / 升级评估 / 外部参考……） | 文件名格式、frontmatter、交给哪个写作 skill | 归类总表·体裁表 |
| ③ 层级 | 涉及**一个对象还是多个**？（单组件 / 单环境 / 跨环境 / 平台级） | 二级及以下目录 | 项目内分类表 |

## 3. 判定规则（核心）

| # | 规则 | 说明 |
|---|---|---|
| R1 | **看主语，不看出处** | 归属由"这篇讲的是什么"决定，不由"在哪个仓库、哪个会话、用哪个工具查到的"决定。 |
| R2 | **换个环境还成立吗** | 换一套环境仍成立的机制、命令、参数 → 通用技术项目（按组件分）；只在本组织特定平台成立的配置链路、环境事实、版本内容 → 该平台项目。 |
| R3 | **一个还是多个** | 只涉及一个环境 / 对象 → 该环境 / 对象目录；涉及多个环境或基线 → 平台级主题目录。不要把跨环境结论塞进某一个环境目录。 |
| R4 | **混合内容先拆再归** | 通用机制与环境事实混在一篇：两部分都能独立成篇 → 拆成两篇、双向互链；否则按"以后会按什么线索找回来"归一处，另一处只留链接。 |
| R5 | **先沿用，后新建** | 已有分类能装下就不新建；不造同义目录（如"故障排查"与"故障手册"、"版本发布"与"版本升级"）；项目内新建子目录不必问，但必须同时登记项目内分类表，并按适配层要求做目录配套动作（具体动作与是否必需都由适配层定）；**新建一级项目必须先问用户**。 |
| R6 | **拿不准就问** | 两个落点都说得通时，给出两个候选和各自依据让用户选；用户的裁决默认**只对本次生效**，用户明确说"以后都这样"才写进裁决先例。 |
| R7 | **故障按组件归，环境进元信息** | 完整故障复盘按出问题的组件归档，环境名写进元信息表与 tags；环境目录下只放该环境的巡检、现状、待办与升级记录。 |
| R8 | **直接落目标位置** | 不先落收件箱再待审中转；收件箱只留工具自动生成的缺口记录。发现收件箱里滞留的笔记，按本 skill 判定后归位。宿主插件若注入了"新知识先经待审区"的沉淀契约，以本规则为准：正式笔记直写目标目录；确被契约拦截时，走完插件流程后立即归位、不留待审，并补齐该流程未带上的元数据。 |

> 口诀：**内容定项目，体裁定命名，范围定层级；能沿用就不新建，拿不准先问。**

**错误做法**

- 按会话来源归类（"在 X 工具里查到的，就放 X 项目"）。
- 为了"结构更完整"预建空目录，或把笔记塞进不贴切的已有目录——分类合不合适由用户判断。
- 把一次性裁决外推成通则（个案不作通则）。
- 移动笔记后只改了文件位置，没改全路径链接和手维护索引。

## 4. 查重与定位（三条必查）

1. **目标项目的目录树** — 确认已有分类，避免造同义目录；
2. **同主题笔记** — 按文件名 / `title` / `summary` / `tags` 查，决定新建还是增量更新；
3. **反向链接** — 要移动的笔记被谁用全路径链过（移动后会断，见 §8 执行顺序）。

路径占位 `<vault>`，实际路径见适配层。下面是 **bash 环境**的参考实现；**执行位置以适配层为准**——默认 shell 不是 bash 时用适配层给的等价命令，不要直接粘这一段（同名命令在不同 shell 下不是同一个程序）。

```bash
# 列出某项目的目录树（排除隐藏目录）
find "<vault>/<项目>" -type d -not -path '*/.*' | sort

# 按关键词查同主题笔记：文件名 + 全文
find "<vault>" -name '*.md' -not -path '*/.*' | grep -i -E '<关键词1>|<关键词2>'
grep -rIln --include='*.md' -E '<关键词1>|<关键词2>' "<vault>" | grep -v '/\.'

# 查某篇笔记被谁链接（移动前必查：全路径链接在移动后会断）
grep -rIn --include='*.md' -F '<文件名不带.md>' "<vault>" | grep -v '/\.'
```

> 上列是**参考实现**不是唯一写法；凡能得出同样三条结论的手段都算数（文档库自带检索、agent 的文件搜索工具、已有的索引工具）。
>
> **查元数据别只按字段所在行匹配**：`tags` 常写成块列表、`summary` 可能写成 `>-` 多行块标量，`^(title|summary|tags):.*关键词` 这类单行正则匹配不到它们——会漏掉同主题笔记、进而重复建页。改用全文搜、库自带检索，或解析 YAML 后取值比较。

查到同主题笔记时：是它的延续 → **增量更新原笔记**（标明新增部分）；是不同侧面 → 新建并互链；结论与之矛盾 → 先核实再改，不让两份冲突结论并存。

## 5. 落地工作流

1. **读**：按 §1 读归类总表、项目内分类表、目标目录现状。
2. **判**：按 §2 三步 + §3 规则得出落点；拿不准按 R6 问。
3. **查重**：按 §4 决定新建、增量更新还是拆分。
4. **定名**：文件名按体裁表的格式；frontmatter 至少满足适配层的最小归类字段。
5. **写**：正文交给对应体裁的写作 skill（未安装时按归类总表里的体裁说明执行）。
6. **落盘**：直接写目标路径；新建目录时登记项目内分类表，并按适配层要求做目录配套动作（适配层没有这项要求就只登记）。
7. **登记**：按适配层的登记对照表，把手维护索引一次登记完；自动生成的索引不手改。
8. **自检**：见 §6。
9. **回写**：本次若新建了分类、确认了新的边界、或用户做了"以后都这样"的裁决 → 按「维护约定」回写。

## 6. 回读自检（写完不算完）

- 落点与 tags 前两位一致（项目、分类对得上）；
- frontmatter 是合法 YAML，`summary` 非空；**用来源分级的库还要有 `origin`**（缺它会被按"本地已验证"处理，检出方式见适配层）；正文首行是一句人话（别以 `##` 节名起头——它是摘要的兜底来源）；
- 每个 wikilink 的目标文件真实存在（按文件名逐个核对，不凭印象）；移动过的笔记，全库没有残留的旧全路径链接；
- 新目录已登记项目内分类表，且适配层要求的目录配套动作已做完；
- 该登记的手维护索引都已登记，且登记的是新路径。

## 7. 归类决定的输出格式

落盘前（或回复用户时）用一行写清决定，便于用户一眼纠正：

```text
归类：<项目> / <体裁> / <目录相对路径>/<文件名>.md ｜ 依据：<R几 + 一句话> ｜ 登记：<要更新的索引>
```

拿不准时给两个候选：

| 候选 | 落点 | 依据 | 代价 |
|---|---|---|---|
| A | … | … | … |
| B | … | … | … |

## 8. 存量巡检（被要求"检查放错位置 / 整理知识库"时）

逐项检查，以编号表汇报；**只报告、不擅自移动**，移动清单经用户确认后再执行。

1. tags 第 1 位与所在一级项目不符的笔记；
2. 按 R2 / R3 / R7 判断放错项目或层级的笔记（给出建议落点与依据）；
3. 收件箱里滞留的非缺口笔记；
4. 同义或近义目录、空目录、只有一篇且可并入上级的目录；
5. 适配层所指的目录配套物中，缺失的目录与配置里已不存在的目录；
6. 指向不存在文件的全路径链接。

执行移动的顺序：备份或留"原路径 → 新路径"清单（**备份完立刻试解压校验，并记下用什么工具打的**，见适配层 §5）→ 移动 → 修全路径链接与手维护索引 → 改 tags 等元数据 → 全库 grep 旧路径确认零残留 → 记操作日志（便于回滚）。

## 9. 触发场景

- 往文档库写任何笔记之前（与写作 skill 配合：本 skill 定"放哪"，写作 skill 定"怎么写"）；
- "这篇放哪""帮我归类""整理一下 Inbox""这个目录结构合理吗""检查有没有放错位置的笔记"；
- 需要新建目录、移动或重命名笔记时。

## 规则

- **归类规则只认文档库里的那一份。** 本 skill 不复制项目边界表；发现别处有过时的落点描述，以库内归类总表为准并提示修正。
- **写作纪律不在这里。** 真实性、命令纪律、文风、内容完整性等跨体裁规则见 `technical-writing`；体裁骨架见 `k8s-obsidian-notes` / `writing-postmortems`。本 skill 只管"放哪"。
- **新建一级项目先问。** 项目内子目录可直接建，但必须同时登记分类表，并按适配层要求做目录配套动作。
- **个案不作通则。** 一次裁决只写进"裁决先例"并注明适用范围，除非用户明确要求，不改写为通用规则。
- **移动可回滚。** 文档库没有版本管理时，批量移动前先备份或留"原路径 → 新路径"清单。
- **只动文档库。** 不改代码仓库、不动集群状态。

## 维护约定（自更新指令）

> **给后续会话：** 归类总表、项目内分类表与本 skill 都是**活文档**。在一次归类工作中若**确证**了下列情况，按对应位置回写：
>
> | 情况 | 回写位置 |
> |---|---|
> | 新建了项目内子目录 | 该项目的项目内分类表（目录、收什么、命名） |
> | 用户对边界做出"以后都这样"的裁决 | 归类总表·裁决先例（日期、裁决、适用范围） |
> | 出现一种新体裁 | 归类总表·体裁表 |
> | 判定规则本身需要修正（新的易错模式） | 本 skill §3（只写通用规则，不写环境值） |
> | 文档库路径、登记点、移动做法变化 | 本 skill `references/local-adaptation.md` |
>
> 只记确证的，不记推测。本 skill 的改动从真源发起再分发（见适配层）。
